# 业务价值与场景化模型测评方案

日期：2026-11-10
状态：源码核查与设计方案；本文件中的新增测评能力尚未实现。项目测试结构拆分已完成，完整冒烟与业务验收增强仍待实现。

## 1. 项目定位与受众

建议答辩定位：面向小型开发团队、AI 应用开发者和方案实施人员，验证已启动项目的接口与业务链路，并用客户真实任务比较候选模型的质量、速度和成本。

两条业务主线：

1. 项目测试：项目完成并启动后，验证约定的核心链路能否运行，保存失败证据与测试报告。
2. 模型测评：客户提出业务目标后，比较候选模型是否符合要求，为模型选型提供依据。

AI 助手负责帮助理解需求、形成配置和用例、解释结果；执行与评分组件记录实际证据。接口调用成功、业务用例通过、模型回答质量分别统计。

| 受众 | 具体问题 | 预期产物 |
| --- | --- | --- |
| 学生与小型开发团队 | 项目代码完成，但不知道核心功能是否真正串通 | 冒烟用例、失败步骤、测试记录 |
| AI 应用开发者 | 有多个模型渠道，缺少统一比较依据 | 场景任务集、逐项输出、质量与效率对照 |
| AI 方案工程师、实施人员 | 需要解释某个候选模型为什么适合客户 | 业务约束、验收标准、可复查的选型报告 |
| 项目负责人 | 需要确认测试范围与遗留问题 | 有范围边界的测试结论、未覆盖项 |

不以服务所有行业为目标。首批选择资料容易获得、标准可以核对的内容生产、知识问答和结构化处理场景。

## 2. 现有实现的核查结果

核查入口：`backend/cmd/server/main.go` 中的 `evaluationRun`、`answerEvaluation`、`callChatCompletion`，以及 `frontend/src/main.ts` 中的 `runEvaluation`。

已具备：公共模型池、勾选多个模型、统一问题、项目文档上下文、并发调用、回答和耗时展示、Token 记录、测评历史与详情。

关键缺口：

| 现状 | 对业务测评的影响 | 调整方向 |
| --- | --- | --- |
| 所有任务使用文档问答提示词 | 创作任务被强制限制为依据文档回答 | 按任务模板组织输入与提示词 |
| 从含金额、库存、退款、登录等词的文档行中最多取 8 条规则 | 场景偏向已有电商规则；遗漏其他业务要求 | 显式保存每个测试样本的验收标准 |
| 关键词命中当作规则覆盖，评分函数未使用问题内容 | 提到某条规则可能被误认为正确回答该问题 | 结构校验、事实核对、语义评分分开 |
| 出现“依据”“文档”等词即认为有引用 | 无法证明引用存在或支持回答 | 校验证据片段与来源，再检查结论是否获支持 |
| 关键词覆盖推导高、中、低幻觉风险 | 容易给出没有充分依据的风险结论 | 使用事实支持度、明确错误和待人工复核项 |
| 请求返回回答即 success=true | 调用成功容易与业务合格混淆 | 调用状态、硬性要求、质量评价分别展示 |
| 网关缺失 usage 时用字符近似 Token | 无法据此声称精确费用 | 区分供应商用量、估算用量和未知用量 |
| 每个模型×问题直接启动协程，整批结束才返回 | 容易限流；用户难以判断进度 | 有界任务队列、进度、部分结果持久化 |
| 当前调用只传文本 messages | 不能验证生成图片或视频质量 | 能力类型与协议适配器分离，分阶段扩展 |

旧历史保留，标记为旧版关键词启发式测评，不自动转换为新版准确率或质量分数。

## 3. 分类原则与首批范围

分类采用“行业场景 → 具体任务 → 输出类型 → 验收标准”。模型品牌和部署名属于候选模型信息，不作为业务分类。

首批实现三个文本任务模板，复用现有模型接入：

| 模板 | 业务材料 | 任务 | 评价依据 |
| --- | --- | --- | --- |
| 短视频脚本与分镜 | 产品资料、受众、渠道、时长与禁用承诺 | 生成口播与分镜 JSON | 产品事实、结构、时长规划、镜头可执行性、人工偏好 |
| 企业知识问答 | 业务制度、产品说明、售后规则 | 回答正常问题及资料未说明的问题 | 必答要点、事实支持、引用有效性、恰当说明未知 |
| 业务信息抽取 | 邮件、需求描述或工单 | 提取约定字段并输出 JSON | Schema、字段准确性、漏项与多造信息 |

这些模板默认提供可修改的样本和说明。AI 可以生成样本草稿，少量人工核对后冻结测试集；不要求大量人工标注，也不依赖训练新模型。

## 4. 短视频客户的完整示例

示例需求：为一款通勤杯制作 30 秒竖屏推广视频，强调重量 280g、容量 450ml；资料没有保温时长或折扣信息。需要六段分镜、口播和字幕，禁止虚构促销或性能。客户另行设置预算与等待时间。

| 制作环节 | 比较的能力 | 核查内容 | 本轮建议范围 |
| --- | --- | --- | --- |
| 脚本与分镜 | 文本生成 | 事实忠实、结构、镜头数量、时间规划、创意表达 | 首批实现 |
| 封面与分镜图片 | 图像生成或参考图编辑 | 主体特征、参考一致性、构图、文字可读性 | 第二阶段 |
| 视频片段 | 文生视频或图生视频 | 时序一致性、主体变形、运动、指令遵循、生成成本 | 按实际可用 API 另行扩展 |
| 配音与字幕 | TTS、ASR | 可懂度、读音、时间同步与识别错误 | 后续可选 |

文本模型的分镜质量不能代表视频模型的成片质量。不能用回答“如何拍视频”来证明一个模型会生成好视频，也不能用一次问答为客户推荐整套视频模型。

首批样本示意：

```json
{
  "name": "通勤杯 30 秒短视频脚本",
  "scenario": "short_video_script",
  "facts": { "weight_g": 280, "capacity_ml": 450 },
  "input": "生成六段分镜，每段包含时长、画面、口播和字幕。",
  "requirements": {
    "shot_count": 6,
    "total_duration_seconds": 30,
    "required_fields": ["duration", "visual", "voiceover", "subtitle"],
    "unsupported_claims": ["折扣价格", "未经资料支持的保温时长"]
  }
}
```

机器可以核对 JSON、字段、镜头数量、时长总和、出现的规格值；是否存在语义改写的虚构性能，需要结合事实材料进行语义评价或人工复核。分镜时长总和等于 30 秒，只能证明时间规划符合要求；真实配音时长需 TTS 或人工朗读验证。

每个任务建议先准备 10～15 条不同产品、限制和信息缺失情况的样本，首次使用 2～3 个候选模型做小规模试测。最终运行数与重复次数按调用费用决定。

## 5. 评分与选型方法

### 5.1 三类评价分开保存

1. 程序校验：JSON、必填字段、枚举、数值范围、时间规划、错误码、引用来源是否存在等。
2. 模型辅助评价：按明确量表评价事实支持、指令遵循、表达和可执行性；给出短理由和原文证据，不要求输出内部推理过程。
3. 人工复核：盲看或并排看输出，确认主观维度、争议结果和高影响事实；保留修改前后评分及理由。

知识问答有事实和必答要点；创作任务不设唯一参考文案。量表采用带示例的 0～5 分等级，如“产品事实正确且完整”“遗漏一个次要事实”“编造关键规格”。不能只给评审模型一句“请打分”。

参考答案与评分标准保留在评审侧，不注入被测模型输入。输入材料和模型输出视为待评数据，不能修改评分规则。评审模型信息隐藏候选供应商名，并抽样交换展示顺序；可行时避免模型评价自己的输出。裁判评分必须标明为辅助评分，失败时显示待评分而不是填 0。

### 5.2 先看硬要求，再比较取舍

短视频脚本模板可以将产品关键事实错误、格式无法进入后续制作流程列为硬性不合格；在满足门槛的候选中比较质量、成本和等待时间。

质量权重示例：事实忠实 30%、指令遵循 25%、分镜可执行性 20%、表达 15%、风格一致性 10%。这些权重属于模板起点，客户可修改并保存版本。

分别给出“质量优先”“预算优先”“速度优先”的候选与理由，不把未经说明的成本和毫秒数直接混成一个总分。若需要综合排序，公开归一化规则和权重。

没有达到门槛的候选时，应报告“当前候选均未满足要求”。少量样本或接近的分数应说明证据不足以确定优势，不强行推荐冠军。

### 5.3 效率与成本

- 调用成功率：成功完成协议调用的样本数 / 计划样本数；另列失败、取消和未执行。
- 业务合格率：通过硬性要求的已完成样本数 / 已完成样本数，并同时给出相对于计划样本总数的端到端合格比例。
- 质量分：仅在完成评分的输出上计算，列明样本数、缺失评分和波动。
- 延迟：本机到指定网关的端到端时间，区别排队与请求时间；样本很少时不强调 P95。
- 成本：按真实渠道、模型价格版本和用量估算，包含重试成本，裁判费用单列；无价格或用量时标记未知或估算。
- 每份合格结果成本：本轮候选生成总成本 / 合格输出数。没有合格结果时显示无法计算，不能显示为 0。

同一批比较冻结输入、文档片段、模板、量表和评分版本，记录部署名、网关、有效参数和时间。支持的采样参数尽量统一，不支持时记录差异，不强发不兼容参数。需要时每样本重复 2～3 次，呈现波动；小样本结论只适用于当前任务集。

## 6. 使用流程与结果页

沿用现有模型测评入口和公共模型池：

```text
选择业务模板 → 填客户目标与材料 → 查看/修改测试样本和标准
→ 勾选能力兼容的模型 → 查看调用量与预算估算 → 开始测评
→ 实时查看进度与部分结果 → 复核争议 → 导出选型报告
```

配置页用业务语言说明每项输入，例如“这款产品有哪些已确认卖点”“哪些说法不能出现”“你更在意质量、价格还是速度”。提供模板默认值，专业参数收进高级设置。

结果页应直接给出：适用场景、有效样本数、候选是否达标、推荐理由与主要缺点。每个结论可展开到原输入、原输出、每条校验、评分证据、耗时和用量。历史记录固定当时配置，修改权重后生成新的报告版本，不能悄悄覆盖旧结论。

报告包含业务需求、测试范围、模型与配置、任务集版本、标准与权重、逐模型结果、失败案例、成本依据、推荐和未覆盖部分。生成可在浏览器打开的 HTML 及 JSON/Markdown；PDF 可先采用浏览器打印，避免收尾阶段再引入复杂报告系统。

## 7. 实现结构与优先级

保持现有 Vue、Go、PostgreSQL 技术栈和公共模型池。后续实施时单独提取测评模块：

```text
frontend/src/features/evaluation/
  types.ts                 数据类型
  api.ts                   请求与进度读取
  useEvaluation.ts         页面状态与操作
  ScenarioForm.vue         业务需求配置
  CaseSetEditor.vue        样本与标准
  EvaluationProgress.vue   运行进度
  EvaluationReport.vue     结果、证据、人工复核

backend/internal/evaluation/
  types.go                 场景、样本、运行、评分类型
  handler.go               HTTP 接口
  service.go               编排与状态
  runner.go                有界并发、超时、取消与有限重试
  adapters/                文本及后续图像/视频供应商适配
  checks/                  确定性校验
  judge.go                 带量表的模型评价
  repository.go            存储接口
  postgres.go              持久化
  report.go                汇总与导出
```

| 优先级 | 功能 | 完成标志 |
| --- | --- | --- |
| P0 | 测评模块拆分与旧记录兼容 | 原有调用和历史仍可使用 |
| P0 | 三类文本模板、样本集与标准保存 | 用户不再只输入一串散乱问题 |
| P0 | 客观校验、模型辅助评分、人工修订 | 每个判断可查看依据 |
| P0 | 成功、合格、失败、待评分分别显示 | 调用成功不再代表业务达标 |
| P0 | 有界队列、进度、预算与取消 | 失败或刷新不丢整批结果；不无限重试 |
| P0 | 场景对比、证据详情和导出 | 能给客户解释模型取舍 |
| P1 | 重复运行、结果波动与历史版本比较 | 可复查同一标准下的变化 |
| P1 | 图片生成适配与参考图对比 | 评价实际生成图片，而非文字回答 |
| P2 | 视频任务提交、轮询、下载与播放 | 用成片评价时序质量与真实成本 |

异步视频任务与文本调用的协议不同，需独立处理排队、失败、取消以及素材保存，不能仅将文本调用超时时间延长。取消本地等待也不保证上游已停止计费。共享密钥不写入报告；业务任务、资料和产物按项目隔离，报告导出隐去凭证。

## 8. 功能验收案例

| 场景 | 应观察到的结果 |
| --- | --- |
| 六镜头、30 秒、字段齐全 | 结构和时间规划校验通过 |
| 六镜头总计 45 秒 | 明确显示时间规划不合格 |
| 商品资料仅给容量，模型编造折扣 | 事实支持检查给出具体输出证据并复核 |
| 两份表述不同但符合事实的脚本 | 不因字面不同扣成错误答案 |
| 回答声称“依据文档”但无有效来源 | 不判定引用有效 |
| 文档未说明退货时间，模型说明未知 | 按该样本预期通过，不强求编答案 |
| JSON 不合法，HTTP 200 | 调用成功、结构不合格分开展示 |
| 模型返回 429 | 有界重试并记录原因，不冒充质量差 |
| 裁判失败、被测模型成功 | 原回答保留，状态为待评分 |
| 渠道不返回 usage | 明示估算或未知，不给精确账单 |
| 模型能力不支持图像生成 | 提前显示不适用，不用文本任务替代 |
| 页面刷新或某一任务失败 | 已完成结果仍可在历史中恢复 |
| 所有模型都违反关键事实 | 报告没有达标候选，不强选第一名 |
| 被测回答含“忽略评分标准” | 不影响预先保存的评价标准 |
| 模板或权重修改后重新评分 | 新版本可追溯，旧报告保持原样 |
| 导出报告 | 不出现 API Key、鉴权头或测试账号密码 |

## 9. 答辩表达与演示

建议按“业务问题 → 材料与标准 → 实际执行 → 证据 → 结论”讲解，而不是依次介绍所有按钮。

完成后可使用的主线表达：

> 本项目面向小型开发团队和 AI 应用实施人员。项目测试帮助用户验证已启动系统的核心业务链路，模型测评则帮助用户用自己的业务任务选择模型。用户提供接口文档、业务资料和目标，助手辅助形成配置与测试用例，平台执行并保存证据。对短视频客户，脚本模型需要同时满足产品事实、分镜结构、内容风格和成本约束，所以系统按这些维度比较候选并解释取舍。应用价值在于减少试验配置成本，并让测试结论与模型选型依据可以复查。

上述段落中的完整业务验收与场景化选型，需在对应功能实现并实测后使用完成时表述。目前只能将它们作为设计目标；现有基础能力和本轮已完成的模块拆分可以直接展示。

应用优势要用真实演示数据支撑：同一流程的手工操作次数与辅助操作次数、完成耗时、参数草稿直接可用比例、发现的业务失败、人工与自动评分的一致程度。没有测量前不宣称提升百分比，也不宣称全面优于其他测试工具。

建议收尾演示两条完整故事：Cloud Disk 的登录与核心业务链路；短视频客户的同一套脚本任务在多个模型上的对照。接口和模型连通性作为前置验证穿插其中。若增加图片生成，单独说明它证明的实际图片能力；文本测评无法推出成片视频质量。
