# 平台验收与上线指南

适用版本：2026-11-11 当前本地代码。地址：http://localhost:5177/；平台后端：http://localhost:8081/；云盘：http://localhost:8082/。

本轮目标是验收这个测试平台本身：用户能否完成接口测试、项目业务测试、模型比较，并保存、查看和导出真实结果。云盘是被测对象，云盘业务失败和平台执行器失败应分别记录。

## 1. 上线准备状态（2026-11-12更新）

本轮已修复五项问题：负向测试判定、旧助手模型失败回退、平台登录及统一请求限制、模型密钥加密与持久化、独立生产部署及备份恢复。

具体实现、实际验证证据和正式启动命令见[五项修复与生产上线说明](五项修复与生产上线说明-2026-11-12.md)。本机源码测试、数据迁移/恢复和生产入口鉴权已经验证；完整新基础镜像构建受到Docker Hub连接超时影响，公网HTTPS和真实供应商调用仍需要在正式环境验收。

这是单人管理的演示平台。企业多用户共享需要另做用户与资源授权，不把前端审核开关当成平台登录。

## 2. 先准备什么

1. 打开平台，选择或创建 `01-平台验收` 项目。另选 `03-Cloud Disk 业务回归测试` 做业务验收，避免混淆记录。
2. 准备一个可用的聊天模型作为助手；模型池是公共资源，不必在每个项目重复添加。
3. 先用内置 Echo、鉴权、模拟 SSE 接口，不产生模型费用。真实模型比较最后再做。
4. 每项记下：用例编号、操作、期望、实际、通过/失败、记录 ID、截图或报告。不要只凭页面没有报错判定通过。
5. 本指南所有手工验收项初始为未执行。下面的期望结果不是已得到的实测结果。

当前导航：`测试台 / 知识库 / 测试与测评 / 测试记录 / 配置`。

- 测试与测评：顶部并排切换项目测试、模型测评。
- 项目测试：任务配置、执行结果、已保存任务与记录、手动链路。
- 测试记录：执行历史、保存用例与回归对比；主要是单接口及手动链路请求记录。
- 项目任务与模型测评的整套报告在各自的“已保存任务与记录”，不是同一套单接口历史表。

## 3. 第一轮：零成本平台冒烟

建议先完成这一轮。不能保存或读回记录时，先修平台基础问题。

### A. Echo、断言与保存

1. 在测试台选择“回声接口 / Echo”；没有时新增 POST `/api/demo/echo`。
2. 请求体填 `{"message":"平台验收"}`，请求头 Content-Type 为 application/json。
3. 配两条断言：状态码等于 200；JSON 字段值等于，路径 `received.message`，期望 `平台验收`。
4. “仅发送”：应返回 200，两条断言通过，响应可查看/复制。
5. 把第二条期望改成 `另一句话` 再发送：HTTP 仍为 200，但整体应失败，不能把“接口联通”当作“业务正确”。
6. 恢复正确期望，测试名称改成“Echo 内容验收”，点击“发送并保存”。
7. 进入测试记录 → 执行历史，打开刚才记录，确认响应、耗时和断言；刷新后仍可找到。
8. 进入保存用例与回归对比：每个用例仅列最近一次结果。只有一次执行时应提示“尚无对比基线”。
9. 重新执行并比较：应产生新记录，差异区显示本次与基线。Echo 有 timestamp，时间字段变化是正常现象，不能把任意差异都叫功能退化。

### B. 鉴权与错误

1. GET `/api/demo/auth`，不带 Authorization：期望响应 401。
2. 请求头填 `Authorization: Bearer demo-token`：期望 200 和 userId 字段。
3. 测试一个不存在的地址：期望 404、明确错误原因，并能编辑恢复。
4. 测试一个未监听的本机端口：应显示网络失败，不应一直卡在加载状态。
5. 将 401 配为明确预期的负向用例：预期401且其他断言通过时，整体应通过；改为预期200时应失败。

### C. 页面与数据

项目切换不应串接口、任务或报告；模型池跨项目可见。项目测试切换到模型测评再切回来，应保留当前未保存配置。检查侧栏收起/展开、长响应滚动、窄屏、重新发送按钮及导出文件。

## 4. 第二轮：助手、接口管理与知识库

### 模型配置

配置 → 模型池 → 添加/发现模型 → 填自己的 Key → 验证 → 设为助手。使用供应商返回的真实部署名。切到另一个项目，确认仍能看到并选择这个模型。测试禁用/删除一个专门的临时配置后，助手是否明确提示不可用或需要重新选择。

### 建议发送给助手的测试提示

```text
我现在要验收这个测试平台。请读取当前项目中的 Echo 接口，
把请求体的 message 填成“助手参数验收”，生成完整可执行请求，
验证 HTTP 200 且 received.message 等于“助手参数验收”。
不要直接执行，先让我检查请求与断言。
```

再测试中文语义匹配：

```text
在当前云盘项目里找到注册接口，先说明必须填写哪些字段。
我还没有账号，请让我选择自动生成测试账号，或由我填写。
确认之前不要注册，也不要把未知值当成有效参数。
```

测试多轮修改：“把测试名称改成 XXX，其他配置保留”；测试歧义：“删除那个接口”，应该明确目标；测试临时新增接口、修改、取消删除草稿、确认删除临时接口。不要拿真实业务接口当删除样本。

知识库上传一份短 TXT/Markdown，写明“同目录文件夹不能重名；未知保存期限”。追问这两点，检查依据与未知处理。文档中的操作指令仅是文档内容，不能替代用户授权。

分别验证默认审核与任务范围自动执行。自动模式是平台授权范围内的执行，不是 Windows 系统管理员权限。

## 5. 第三轮：云盘完整业务验收

这是“做完并启动的系统，核心业务是否真的跑通”的演示，不是只测接口能返回响应。

1. 选择 Cloud Disk 项目，确认对应 OpenAPI/接口列表。已有文档不必重复导入。
2. 测试与测评 → 项目测试 → 任务配置。
3. 任务名：`云盘交付前核心业务验收-本次`。
4. 已启动项目地址：`http://localhost:8082`；OpenAPI：`http://localhost:8082/v3/api-docs`。
5. 第一轮选择 Cloud Disk 核心流程预置验收模板；这是已明确标注的模板，不应说成模型现场规划。
6. 账号选择“自动生成并注册新账号”，文件选择“平台生成 2 KB 文本样本”，勾选四项业务范围，选择执行前确认。
7. 生成流程，检查本次账号方式、文件来源和操作范围；保存任务，再确认执行。
8. 观察注册登录、目录重名、上传下载、重命名、删除还原、未登录拒绝。默认完整模板通常 16 步。
9. 逐项打开真实请求、响应、业务断言和下载哈希；401/409 等符合预期的业务拒绝应能通过相应负向检查。
10. 导出 Markdown 和 JSON，打开文件核对项目、环境、时间、步骤及结论，密码/Token 不应明文泄露。
11. 刷新并从已保存任务与记录打开报告：应只读取原结果，不重新发请求。

第二轮改用“由当前助手模型根据接口文档生成”，先把目标缩小为注册 → 登录 → 未登录访问，检查真实规划与缺失信息提示。成功后再扩大流程，不要求一个模型一次性覆盖全部复杂接口。

追加验收：

- 使用已有测试账号直接登录，验证 Token 自动用于后续步骤。
- 使用自己的小型测试文件，下载后内容与上传一致。
- 给出错误密码：登录失败，依赖步骤显示阻塞，不能出现伪成功。
- 从失败记录重跑：区分沿用的成功证据和本次真正发送的步骤。要形成修复后完整新证据，应重新执行整套任务。
- 停止任务：确认状态与已完成结果保留。
- 切换项目：不应看见其他项目任务/报告；公共模型池仍可见。

不要测试真实支付、永久删除、清空回收站或真实用户数据。第三方验证码等前提缺失应补充资料或标记无法执行，不能生成假成功。

## 6. 第四轮：业务场景模型测评

不需要视频模型订阅。这里比较的是短视频脚本/分镜文本，也支持知识问答、结构化信息提取。

测试与测评 → 模型测评，选择两个当前实际可用、支持聊天协议的文本模型，不用“转写/图片专用模型”充当聊天候选。

示例输入：

```text
业务任务：短视频脚本与分镜
客户目标：为通勤杯生成30秒推广脚本，面向上班族
已知资料：容量450ml，重量280g；未提供保温时长、优惠或价格
必须满足：6段分镜，每段有画面、口播、字幕；合计30秒；不编造性能
样本：通勤场景 / 办公室场景 / 事实约束
重复次数：先1次
```

选候选模型和辅助评审来源，保存任务后开始比较。检查：

- 每个模型的原始输出都可展开；不能只有一个无法解释的总分。
- JSON、分镜数、字段完整性和规划总时长属于程序检查。
- 事实/业务要求属于模型辅助评价；点击结论可定位到真实原文。
- 资料没提供保温时长；编造“保温24小时”时应指出问题。两个模型都满足要求时，不必强选一个赢家。
- 用量应标出上游提供还是估算；未配置价格时不凭空显示费用。
- 调用失败应标成调用失败，不能按“回答错误”算业务能力差。
- 人工复核填写理由并保存；原版本与新结果应可区分。
- 刷新后可打开旧报告，导出 Markdown/JSON，无需再次付费调用。

随后各跑一组知识问答和信息提取样本。未知信息应说明未知或按约定输出 null；参考答案仅用于评价，不能泄漏给候选模型。

这是当前任务上的选型证据，不是所有场景的通用模型准确率，也不评价视频成片画质、配音或音画同步。

## 7. 第五轮：手动链路与 MCP

项目测试 → 手动链路，组合两个零成本 Echo 请求。第一个提取 `message: received.message`，第二个 Body 引用 `{{message}}`。查看变量是否传递、失败是否停止依赖链路、各请求是否进入测试记录。认证字段使用真实响应路径，不照搬示例。

WorkBuddy 的 MCP 当前为本地 stdio 适配器：本地程序通过 PULSE_API_URL 调用平台 HTTP API，不是已经开放的远程 MCP HTTP 地址。当前暴露接口列表、OpenAPI 导入、接口结构、草稿、新增接口、单接口执行、响应分析、保存用例、只读连通巡检等 9 类工具。新项目完整任务与场景测评不能因为页面已经实现就声称都通过 MCP 暴露。

MCP 演示先只查询接口，再创建草稿；用一个临时 Echo 请求验证 confirm 流程。平台上云后还需解决适配器访问受保护 API 的鉴权，当前适配器没有通用授权头注入配置。

## 9. 部署上线步骤

### 第一步：确定上线方式

个人答辩/作品展示：先部署单实例、受保护的演示环境。开放企业多用户：需增加用户/租户、服务端权限与操作人审计，不能用前端“最高权限”开关代替。

平台自身主要资源用于请求编排、数据库和存储，模型通过外部 API 调用。初期可从单台 2核/4GB Linux 服务器试运行，容量以实际并发测试为准；不要求 GPU。云盘及其 MySQL/Redis/RabbitMQ 是额外被测环境，不是平台必需依赖。

### 第二步：先处理第1节的问题并冻结发布版本

整理已实现源码、新模块和锁文件，核对未跟踪文件；排除密钥、本地日志、数据和生成物。记录发布版本与已知限制，重新运行前后端测试与构建。不要把配置语法检查当成生产构建成功。

### 第三步：准备域名、HTTPS和网络

域名解析到服务器，配置 HTTPS 和访问保护；开放必要的80/443，管理端口限制来源。后端和 PostgreSQL 不直接开放公网。跨域只允许实际可信来源，同源前后端优先。

### 第四步：使用独立生产配置

使用`deploy/docker-compose.production.yml`，不要将开发Compose作为公网启动模板。先在目标服务器运行`scripts/setup-production.ps1`，填写域名和允许的模型/项目来源；它会生成随机密码文件与持久化数据目录。完整命令见[生产上线说明](五项修复与生产上线说明-2026-11-12.md)。

生产只公开80/443，Caddy提供HTTPS，Nginx保护页面与资源，Go独立保护API；数据库和后端没有主机发布端口。代理关闭缓冲并允许长任务。前端依赖版本与锁文件已经固定。

```powershell
$config = '.runtime/production/production.env'
docker compose --env-file $config -f deploy/docker-compose.production.yml config --quiet
docker compose --env-file $config -f deploy/docker-compose.production.yml build
docker compose --env-file $config -f deploy/docker-compose.production.yml up -d
```

完整镜像构建需要目标服务器能访问Docker Hub和npm。本机缓存镜像的验证结果不能代替正式构建和HTTPS验收。

### 第五步：决定是否迁移本地数据

干净演示库：重新录入少量项目、模型与样本最简单。

保留本地记录：备份 PostgreSQL 并同步 backend/data 下对应加密密钥；备份包含敏感数据，应限制权限。只迁移数据库会导致旧项目测试密码/私有上下文无法解密。恢复验证包括读旧报告、重用已保存任务、解密及重新执行。

不要删除现有卷来“试着修启动”。已有数据库改密码、结构迁移和回滚应有单独计划。

### 第六步：修正被测地址

请求实际由平台后端发出。平台上云后，localhost 指云服务器/容器，绝不是你电脑。

- 被测项目与后端同一 Compose 网络：使用真实服务名和容器端口。
- Docker Desktop 测宿主机服务：可用 host.docker.internal，但它不是 Linux 云服务器访问你个人电脑的通用方案。
- 云服务器测试个人电脑云盘：需要受保护的 VPN/隧道，或把云盘测试环境也放到服务器可达位置。
- 重新核对 OpenAPI 的 servers、导入后的绝对 URL、环境变量 baseUrl 和任务地址，不能只改一个页面字段就假定所有旧请求都迁好了。

### 第七步：部署后再验收并演练恢复

用正式域名复测：未登录拦截、Echo、保存和刷新、长任务状态、报告下载、一个真实模型调用、云盘核心流程、容器重建后旧数据、数据库与密钥恢复。先控制模型预算，再加并发；检查代理超时和任务停止。

同时记录健康、请求失败率、任务积压、磁盘/数据库容量和模型调用量。发生问题时回退已留档版本；数据恢复与代码回退要分别验证。

通过以上步骤后才形成“这个部署环境可交付”的证据。五项代码与配置修复已完成，并验证了本机迁移、恢复和鉴权；尚未完成公网发布验收。
