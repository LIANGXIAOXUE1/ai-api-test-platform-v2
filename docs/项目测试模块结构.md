# 项目测试模块结构

更新日期：2026-11-10

本轮完成现有项目测试功能的结构拆分，保留原有连通性巡检、审核、历史和报告行为。被测项目只需启动且能被平台访问，不要求部署上线。完整冒烟链路和业务验收能力属于下一阶段。

## 前端结构

路径：`frontend/src/features/project-test/`

| 文件 | 职责 |
| --- | --- |
| `types.ts` | 请求、报告、审核草稿及权限类型 |
| `api.ts` | 项目巡检、历史列表、OpenAPI 导入的 API 调用 |
| `useProjectTest.ts` | 模块状态、生成审核草稿、确认执行、恢复历史、协调报告导出 |
| `ProjectTestAssistant.vue` | 现有助手内的计划、结果、待审核接口和历史卡片；通过事件请求操作 |
| `ProjectTestPanel.vue` | 从旧模板抽出的独立面板；保持原有隐藏条件，不增加入口或 Agent |
| `report.ts` | Markdown 保存位置选择及浏览器下载兼容处理 |
| `intent.ts` | 原有连通性任务识别逻辑，未新增规则或调整语义路由 |

`frontend/src/main.ts` 注册组件、创建一次 composable，并提供已有项目、权限、环境、刷新和消息回调。项目测试相关视图已从运行时字符串替换中抽出，改为 Vue 单文件组件。其他页面沿用原实现。

人工配置入口 `openManualReview()` 仍在 `main.ts` 中，因为它负责切换现有请求编辑器并加载接口配置。项目测试组件只发送 `review` 事件，不直接修改其他页面状态。

状态属于 `useProjectTest()` 实例，避免模块顶层单例。前端 API 复用注入的现有请求客户端；测试可替换客户端而无需访问真实项目。

## 后端结构

路径：`backend/internal/projecttest/`

| 文件 | 职责 |
| --- | --- |
| `types.go` | 模块数据类型、Repository 存储接口和 ProbeExecutor 执行接口 |
| `handler.go` | HTTP 方法检查、输入解码、参数错误与响应编码 |
| `service.go` | 组织巡检、调用执行器、汇总结果和保存报告 |
| `policy.go` | 原有目标地址判断、localhost 别名处理和风险分类 |
| `postgres.go` | 读取项目接口，保存与查询 PostgreSQL 巡检报告 |
| `report.go` | 提取业务码并生成 Markdown 报告 |
| `policy_test.go` | 目标地址与本地别名测试 |
| `service_test.go` | 执行、审核、失败处理和 HTTP 契约测试 |

`backend/cmd/server/main.go` 负责装配仓库、服务、执行器和路由。`backend/cmd/server/project_test_adapter.go` 将模块执行接口接到现有 `s.execute()` 和 `s.store.addRun()`，复用请求执行与单次记录能力。

依赖方向：

```text
现有助手 / 页面
  → useProjectTest → api.ts
  → handler → service
                  ├─ Repository → PostgreSQL
                  └─ ProbeExecutor → 适配器 → 现有请求执行器与记录存储
```

服务通过接口依赖执行器和存储，不导入 `cmd/server`。以后可以独立测试编排逻辑，也可以在模块内增加业务链路执行服务。

## 保持兼容的部分

- HTTP 路由仍为 `POST /api/project-check`、`GET /api/project-check-reports?projectId=...`；JSON 字段和错误响应保持原有契约。
- 复用现有 `apis` 和 `project_check_reports` 表；建表仍由原数据库启动流程负责，没有新增迁移或重置记录。
- 自动巡检仍仅执行目标项目的 GET、HEAD、OPTIONS 探测，适配器不重放接口配置中保存的请求头、查询参数和请求体。
- 收到 HTTP 响应仍表示“可达”。HTTP 404、401 或业务错误不能据此认定业务测试通过。本轮未改变该判定。
- 保留原有 `review` / `auto` 行为和 `confirmed` 请求字段；后者在旧服务中不是额外执行门槛，本轮未改变此契约。
- 单接口测试、模型池、模型评测、其他 Agent 逻辑、导航和全局样式保持原有实现。
- `deploy/backend.Dockerfile` 仅补充新 `internal` 源码目录的复制，以保持原构建入口可用；没有执行部署。

## 本轮验证

在 `backend` 目录运行 `go test ./...`，覆盖服务器、MCP 和项目测试模块。在 `frontend` 目录运行：

```text
npm.cmd run build
npm.cmd run test:project-test
```

前端 7 条测试覆盖：审核前不执行、确认后按顺序导入与执行、自动模式、缺少地址提示、接口异常后的状态恢复、历史恢复与实例隔离、历史加载失败。

隔离浏览器使用模拟 API 数据验证了助手审核卡片、确认后一次执行、结果显示、待审核列表、人工配置跳转和 Markdown 导出。未向真实云盘服务、模型服务或生产数据库发起业务请求。历史记录恢复由自动化测试覆盖；浏览器历史列表已显示，最终点击复核因调试连接断开未完成。

将新组件边界还原为原模板后，非项目测试页面的模板对比一致；构建输出的全局 CSS 文件哈希与拆分前一致。

原页面已有三个未暴露给模板的 setup 绑定警告：`forwardAssistantWheel`、`assistantDecisionDraft`、`resizeAssistantInput`。已通过拆分前备份确认它们不是本轮引入，本次未扩展到其他助手代码修复。

完整方案见[现有项目测试功能完善方案](交付验收改造方案-2026-11-10.md)。后续可在本模块逐步加入：

2. 按业务依赖执行登录、传递 Token 和资源 ID，区分失败、阻塞及未执行。

这些属于功能增强，本轮结构拆分并未实现。沿用现有助手调用入口，其他功能不需要随之重构。
