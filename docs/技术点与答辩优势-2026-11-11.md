# 技术点与答辩优势

更新：2026-11-16，以平台c4e278c功能基线核对。说明实际能力，验收结果/已知问题以[测试团队交付清单](测试团队交付清单.md)和[验证记录](发布前验证记录-2026-11-16.md)为准。

对应当前平台：基于 AI Agent 的智能 API 测试与评测平台。建议围绕两条业务主线讲解，辅助功能围绕它们组织，不把菜单数量当成创新点。

## 1. 先讲受众和实际问题

主要用户是完成项目后需要交付自检的学生、小团队和开发者，以及需要为客户业务选择文本模型的 AI 应用工程师。

用户遇到的两类问题：

1. 项目能启动，但注册、登录、上传、删除还原等核心业务是否真正跑通缺少证据。
2. 大模型回答看起来都不错，但对客户规定的格式、事实和业务要求，哪些满足、哪些失败很难快速比较。

平台用可保存任务、真实执行记录和可追溯的检查结果回答这两个问题。

## 2. 技术架构及职责

| 层次 | 实际技术/实现 | 对产品的作用 |
| --- | --- | --- |
| 前端 | Vue3、TypeScript、Vite、Vue单文件组件；现有入口仍使用部分运行时模板 | 配置、审核、执行进度、报告与证据查看；不是一个已全面拆完的微前端 |
| 后端 | Go、标准库 net/http；项目测试与评测各有 internal 模块 | 处理请求、任务编排、验证、持久化与模型适配 |
| 数据 | PostgreSQL、pgx驱动；JSONB任务配置/报告 | 保存接口、公共模型池、任务、执行及复核结果 |
| 模型接入 | OpenAI兼容聊天协议与结构化输出/工具配置 | 使用真实模型理解目标和生成草稿，不需要本地GPU训练 |
| 上下文 | 当前项目接口契约、环境信息、文档片段检索 | 减少只靠自然语言猜参数；属于轻量上下文增强，不能直接说成已实现向量检索平台 |
| 执行 | 依赖步骤、变量插值/提取、资源来源校验、业务断言、下载SHA256 | 从“接口有响应”推进到“这次业务按预期完成” |
| 测评 | 程序检查 + 模型辅助评审 + 原文定位 + 人工复核 | 数量/格式与业务语义分开判断，结论有可查看依据 |
| 集成/部署 | 本地stdio MCP、Docker Compose、Nginx | 接外部助手和容器部署；已提供登录、目标限制、加密及备份恢复，正式环境仍须验收 |

实际入口：frontend/src/features/project-test、features/evaluation、features/history；后端 backend/internal/projecttest、internal/evaluation。main.ts 和 cmd/server/main.go 仍承担已有功能与装配，不能宣称全部代码已经彻底解耦。

## 3. Agent 怎么讲

用户目标 → 获取当前项目上下文 → 模型生成结构化草稿/步骤 → 验证目标范围、参数、依赖和缺失信息 → 用户审核或按任务授权执行 → 收集真实反馈 → 保存证据和报告。

模型负责语义理解和生成建议；执行器负责实际调用与判断，数据库负责留档。缺少账号/文件/业务前提时让用户选择自动准备或自己填写，不把缺失信息变成虚构数据。

新项目任务允许模型根据契约规划，结构问题可反馈修正一次；Cloud Disk预置模板是另一个明确标注的入口。审核/自动执行是平台任务范围内授权，不是系统最高权限。

当前助手模型失败明确报错，不回退规则草稿；仍保留旧版测评生成接口，和助手失败处理是不同问题，见DOC-Q01。前端逐字显示与真正模型流式传输也应区分，不要把动画作为后端流式创新。

## 4. 五个有实际证据的优势

1. **准备工作少**：可选择自动生成并注册测试账号、自动生成小型文件；登录Token和资源ID自动传递。展示用户少做了哪些操作，而不是笼统说“全自动”。
2. **检查业务结果**：重名创建被拒绝、下载哈希一致、删除后目录移除、还原后内容一致，比单看HTTP200更接近交付验收。
3. **失败有位置和证据**：报告区分失败、阻塞、未执行；能看预期和实际，不把后续未跑步骤算成成功。
4. **模型比较贴近客户任务**：给出“6段/30秒/不编造性能”的具体要求，再逐项查看各模型输出，而不是展示一个难解释的通用准确率。
5. **结果可复用、可沟通**：配置可保存，旧报告可读取，重新执行产生新证据，Markdown/JSON可作为交付附件；模型结论可带理由人工复核。

MCP属于扩展集成优势，可补充演示接口查询、草稿和受控测试；当前9类工具不能代替完整新任务的全部能力。

## 5. 5～8分钟演示建议

1. 约1分钟：Echo正常/错误断言，证明平台有真实执行和判断，不是聊天演示。
2. 约2～3分钟：云盘自动账号+自动文件，展示完整任务报告的注册登录、上传下载、重名和还原。运行较慢时打开提前保存的真实报告，并说明执行时间。
3. 约2分钟：通勤杯脚本比较，点击程序检查、原文及事实证据；再展示一个人工复核或明确调用失败案例。
4. 约1分钟：打开历史报告和导出文件，强调查看不会再次执行/扣模型费用。
5. 可选：MCP只读查询；图片API只演示一条已保存的真实结果，避免重复付费占用主线时间。

报告里的结果必须来自实际执行。预置样本不等于实测成绩；过去成功不等于当天环境成功；若演示旧报告，明确说明是哪个环境、哪次执行。

## 6. 可以直接讲的一段话

> 我的平台面向完成项目后需要验收的开发者，以及需要做模型选型的AI应用人员。第一条线把接口文档、测试账号、文件和业务步骤组织成任务，自动传递Token和资源ID，验证核心业务是否按预期完成，并保留失败位置和真实报告。第二条线按客户的任务和要求比较模型，程序检查格式、数量和时长，模型辅助评价事实与业务要求，用户可以查看原文并复核。平台的重点是减少测试准备和重复操作，同时让“项目是否跑通、模型是否满足需求”有可追溯的证据。

## 7. 应明确承认的边界

- 接口流程通过，不能证明网页按钮、小程序页面、支付收银台和机型兼容都通过。
- 短视频模块评的是脚本/分镜文本，不是视频成片质量；文字规划30秒不是已验证真实配音30秒。
- AI生成的业务标准可能错，需要核对契约/需求；模型评审不是客观真值。
- 覆盖核心任务不等于测试全部接口，也不等于安全/大规模性能验收。
- 负向判定、助手失败处理、鉴权、密钥和部署持久化已有实现及既有证据；旧测评入口、空/部分Token、跨批排队仍需收尾，完整构建/真实AI专项与正式环境验收尚未完成。

展示这些边界能让项目定位更清楚：一个可复用、证据可查的智能接口验收和业务模型比较工具，而不是承诺替代全部软件测试。
